# Advisory catalog and matching contracts

The wire catalog contains a schema version, monotonic revision, issue and expiry times, and reviewed records. Decode reads it in one streaming pass and rejects noncanonical field names, duplicate keys, unknown fields (a rule cannot carry a `variant`), nulls, invalid ranges and invalid dates. It refuses input over 4 MiB, invalid UTF-8 and nesting over 32 levels first. It reads the `records`, `ranges` and `required_features` arrays element by element and stops at the first element past 1,000 records or 32 ranges or features, before decoding that element, so a hostile input costs memory in proportion to the bound and not to its size. Any error returns the zero `Catalog`. Text in a catalog or a report is at most 4,096 bytes of valid UTF-8 with no control character (not C0, DEL or C1) and no invisible or misleading one (a bidirectional control, a zero-width character, a tag character, the no-break space, the line or paragraph separator, the byte order mark and the rest of what `sanitize` escapes; see `report-schema.md`), and every time uses a zero UTC offset, can be written in JSON and is not before 2019-01-01T00:00:00Z. A decoder-derived SHA-256 digest records the exact input bytes outside the wire document. It is the digest of those bytes, not a content identity (another spelling of the same catalog has another digest), and not a self-hash, authentication, or persistent anti-rollback. A trusted import boundary must provide those controls.

Each rule identifies a component and a version role (`api_reported`, `local_cli`, or `running_daemon`), and may require an operating system and named features. A rule names its OS with a canonical value, spelled exactly: `linux`, `windows`, `macos`, `ios`, `tvos`, `android`, `freebsd`, `openbsd`, `illumos`, `solaris`, `plan9`, `js`, `aix`, `dragonfly`, `netbsd`, `tamago` or `wasip1`; any other spelling (`Linux`, `macOS`, `darwin`) fails to decode. A rule cannot name an OS variant. Version facts declare a channel; the matcher compares only a stable release with an even minor (the release grammar below), and gives every other version, an unstable one or a backport included, an unknown finding with the reason. Ranges include `introduced` and exclude `fixed`; one endpoint may be omitted, but not both. Each bound is a bare release `X.Y.Z` with an even minor, because only the stable track is ranged: a bound on the unstable track (an odd minor, such as the unstable fix in the shipped rule's bulletin) and any build suffix are refused. Ranges of one rule may touch (one `fixed` equal to the next `introduced`) but not overlap, and `introduced` must be below `fixed`. A range that can match no release is refused: with `introduced` omitted, `fixed` of `0.0.0` leaves nothing below it. Every catalog rule has its own error text, and an error about a record is prefixed with the record's position. Catalog record IDs need not be CVEs. Publication, update and source-check dates may be absent. Review and review expiry are mandatory. A source check never extends rule review. A stale rule retains positive warnings but cannot establish a fresh negative result. A withdrawn rule produces no finding, and so no clearance and no mitigation text; it is counted. A pending rule produces only `unknown` findings and no mitigation text; it never gives `affected`, `potentially_affected` or `not_affected`. The reason is `review_pending` unless an earlier one applies: the one the evidence had already earned (for example `no_version`), or `catalog_expired` or `review_expired` for a device that would have been cleared.

Release grammar. `parseRelease` defines the version strings a version fact may carry: a release `X.Y.Z` (each component `0` or a number without a leading zero, at most nine digits), optionally followed by the build suffix Tailscale appends, `-t<hex>` or `-t<hex>-g<hex>`, where each `<hex>` is 7 to 40 lowercase hexadecimal digits. It returns the release and drops the suffix, because Tailscale states a fix by release and never by commit; the raw string stays in the evidence. Nothing else is a release: `-g` without `-t`, uppercase or short hex, a `v` prefix, `+`, `-rc` and `-dev` suffixes, spaces, two or four components, leading zeros and components of ten digits are unrecognised builds. A version can be compared with a range only when its channel is `stable` and its minor is even: an unknown channel is `channel_unknown`, and an unstable channel or an odd minor is `unstable_track`. Catalog range bounds use the stricter bare parser, which accepts no suffix.

Operating-system vocabulary. A source reports an OS in its own spelling, and `NormaliseOS` reads it through an exact, case-sensitive table: `linux`, `windows`, `android`, `freebsd`, `openbsd`, `illumos`, `solaris`, `plan9`, `js`, `aix`, `dragonfly`, `netbsd`, `tamago` and `wasip1` read as themselves, `macOS` and `darwin` as `macos`, `iOS` and `ios` as `ios`, and `tvOS` as `tvos`. These are the spellings of Tailscale's `version.OS()` (`tvOS`, `iOS` and `macOS` on Apple platforms, Go's `GOOS` elsewhere), read in its source on 30 October 2026, plus the raw `darwin` and `ios` that a local source may report. The six identity entries after `plan9` are Go `GOOS` values that `version.OS()` passes through and that the same repository handles as platforms of their own (the file and line of each are in the comment of `internal/security/platform.go`); the owner added them on that date. A spelling outside the table is never guessed at: `Linux`, `macos`, `zos` and a name with a space are unrecognised (the report schema names that condition `os_unrecognised`), and a new Tailscale spelling stays unrecognised until it is added to the table with its source. A device's platform variant is information for the reader; matching ignores it.

Evidence must have the same context, asset and scope, be marked fresh, be no more than 30 minutes old (observation time, or acquisition time when absent), and carry its stated origin and acquisition time. The running daemon is established by facts of the running-daemon role from local or collector origin. An API-reported version (origin API) counts as daemon evidence too, but only while the same device has a usable `connected_to_control` feature fact (`FeatureConnectedToControl`) of origin API whose value is true: the version evidence and that fact must each pass these checks, including the 30-minute age of the source's own observation. Without that fact (it is absent, false, stale, failed, valueless, from another origin, or the API contradicts itself) the API version stays a fallback that can indicate potential exposure but cannot establish that a daemon is patched. A local CLI report never establishes it: a CLI or API report is read as `runtime_unobserved`. Missing, conflicting or mismatched facts are unknown. Feature or platform evidence can exclude a rule only when its source matches the rule’s version role and its context, asset and scope match: API origin for API-reported rules, and local or collector origin for CLI and daemon rules. Other origins remain conditional. There is one exception, for features (decision D5): for a running-daemon or local-CLI rule a feature fact of origin API speaks as well, but only while the same device passes the guard above (a usable `connected_to_control` = true fact of origin API and no usable false one) and the feature fact itself is usable, including the 30-minute age. Without the guard the API's feature fact is ignored and the feature is unknown; the guard is one test, shared with the API's version. `connected_to_control` is the guard and is never read as a required feature. A usable local or collector fact and a guarded API fact that disagree on one feature leave it unknown (`feature_unknown`, the reason of a feature reported both on and off), so neither can make the device affected or not affected through that feature; a guarded API fact that decides is cited with the `connected_to_control` fact that opened the guard. An expired or not-yet-valid catalog, or a stale or unapproved rule, makes catalog coverage partial even when a positive warning is retained. A finding's identity is `FindingID`, a deterministic unkeyed hash of the context, the snapshot's scope, the asset and the rule ID (not the rule revision), so the same device and rule under the local and fleet scopes are two findings; it is not a privacy-preserving pseudonym, a later boundary must provide keyed identity and output sanitization. Catalog deletion does not prove remediation; lifecycle reconciliation is separate.

Matching. `Match` judges every device that a version, platform or feature fact names (a device is named by the asset of its evidence; a fact with no asset is refused as invalid input, since a report could not hold it) by every rule that is not withdrawn, and returns one finding for each pair, in the order of the rules and then of the devices as their facts were first seen: versions, then platforms, then features. A pair the matcher cannot judge is an unknown finding with a reason from the closed set, never an omission, so a device whose evidence is stale or failed is still reported. The facts are indexed by device once, so the work is about the number of rules times the number of facts. Input that is invalid (a nil context, a snapshot or catalog that fails validation, a budget below zero or above 250,000 candidates, where zero means 250,000) returns no findings, no coverage row and an error: nothing was judged.

For one rule and one device the matcher first chooses a release. The candidates are the device's facts for the rule's component with usable evidence. With no fact for the component the finding is `no_version` (evidence state `absent`; so too when the facts have no value, or none has the role and origin the rule needs); with facts that are all unusable it is `evidence_error` when any carries an error and `stale_evidence` otherwise (state `stale`). The exact facts are those whose role is the rule's role from an origin that role allows: local or collector for the running-daemon and CLI roles, API for the API role. For a running-daemon rule the API's report is exact as well while the device is connected to control (R9, above), and every other API report must agree with the exact facts; a local CLI report is ignored whenever an exact fact exists, so it never conflicts with a daemon fact. Without an exact fact, a running-daemon rule falls back on the API and CLI reports. The releases that are compared must all read as releases (`unrecognised_build` otherwise) and be equal (`version_conflict`), and each fact that decides must be on the stable track (`channel_unknown`, `unstable_track`). A fact in the fallback can only warn: a release in range is `potentially_affected` and one outside it `unknown`, both with the reason `runtime_unobserved`, and a conflict between the API and CLI reports is `version_conflict`.

An exact release outside every range is `not_affected`; the operating system and features are then not looked at. An exact release in range is `affected` when the rule's operating-system and feature conditions are all known to hold, `not_affected` when any is known to be false (from usable evidence whose origin matches the rule's role), and otherwise `potentially_affected` for the first unknown condition: `os_unrecognised` (a spelling outside the vocabulary, alone or beside others), `os_unknown` (no usable platform fact with an OS, or platform facts that disagree) or `feature_unknown` (a required feature with no usable fact, or reported both on and off). Platform evidence of an origin that does not match the rule's role says nothing. Only after this is the state of the catalog and the rule applied, and only to a result that is not already unknown, which keeps its reason: a catalog or a review that is not fresh turns `not_affected` into `unknown` (`catalog_expired`, then `review_expired`), an `affected` or `potentially_affected` result is kept with an explanation that the review is stale, and a pending rule turns what remains into `unknown` (`review_pending`). The mitigation text is attached to `affected` and `potentially_affected` findings only. The evidence state is `observed` for `affected`, `not_affected` and `potentially_affected`, `stale` for `stale_evidence`, `absent` for `no_version` and `unknown` otherwise.

The coverage row (catalog dimension, the snapshot's scope and context, source `advisory catalog`) always carries counts: the rules evaluated (approved and pending), the withdrawn rules skipped, the devices, the findings and how many are unknown or potentially affected. It is `complete` only if the catalog is fresh, every rule evaluated is approved and has a fresh review, at least one rule and one device were evaluated, and no finding is unknown or potentially affected. Otherwise it is `partial` and its explanation names each cause with its count (an expired or not yet valid catalog, no rules, pending rules, rules with a stale review, no devices, and the unknown and potentially affected findings with their reasons). An empty catalog, a catalog of withdrawn rules and a snapshot that names no device are therefore partial. If a run stops after it has started (the context is cancelled, the work budget is spent, or the 10,000-finding limit is reached) it returns the findings so far, a partial row that says where it stopped, with counts of what was evaluated, and the error (`ErrWorkBudget` for either limit); a report built from that output validates.

The matcher evaluates present observations, returns partial evidence and partial coverage with an error on cancellation or work exhaustion, and caps records, ranges, observations, findings and candidate work. It performs no API collection or external calls. `data/advisories/testdata` is synthetic and is not a public advisory feed. Real records require source, rule and fixture review before shipping.

Evaluation. `Evaluate` (`internal/security/evaluate.go`) turns an `Input` (the catalog, the snapshot, the coverage rows the collection reported, an optional intent set, the time and the work budget) into a `Report`. It is pure: no I/O, no clock, no model. It calls `Match`, requests the coverage targets in the snapshot's scope that the input asks for and answers each with a row: the rows the collection reported for versions and features (a dimension it did not describe gets an explicit partial row) and `Match`'s catalog row, which are always requested, and, only when an intent set is supplied, intent. With no intent set the intent is not requested, and the report says so in a row of its own with the status `not_requested`, an explanation (`intent not requested: no intent set is configured`) and a source: the absence is stated, and that row never keeps the report from being complete. Nothing judges an intent set in this version, so a supplied one is requested and its row is partial, `intent not evaluated` (it counts the expectations and repeats none of the set's text, and the report names the set's digest and revision). `security scan` supplies one when the configuration names an invariants file or the command line does (`--invariants FILE`; `--no-invariants` supplies none), reads it before any source is asked, and refuses a configured file it cannot read, decode or adapt (`config_invalid`; `config_unsafe` for a file with the wrong owner or mode, both exit 6) rather than taking it for no intent. The report is `complete` only when every requested target has a complete row and no row is partial: a pending rule, a stale review, an unknown or potentially affected finding or a source that failed each keep it partial, with its findings, and the coverage says why. With the four TS-2026 rules shipping pending, their `unknown` findings keep the catalog row partial, so a scan by the shipped catalog is partial (and exits 8 or 1) until the owner approves them. There is no global safety badge or score. Findings are ordered affected, then potentially affected, then unknown, then not affected, and by source severity (critical first) within each, otherwise in `Match`'s order. The evaluation has a five-second budget, `EvaluationBudget`, enforced in the loop that does the work: `Match` polls the context at every step, so when the budget ends the run stops and no goroutine is left behind. A run stopped by the budget, by the work cap in the input or by the 10,000-finding limit returns the findings so far in a partial report that says where it stopped, with no error; one stopped because the caller's context ended returns that report and the context's error. The work cap is the matcher's own (`MaxCandidates`, 250,000) and is not raised. The report owns its data: it shares no slice or pointer with the input. `CountAtThreshold` counts the affected and potentially affected findings at or above a severity threshold (an unknown severity is above every threshold) over the whole report, and `Truncate` cuts a report to a number of findings, sets `Truncated`, keeps `TotalFindings` and the counts of the catalog row, and makes the status partial; count first, then truncate, so the output limit cannot move the count. `tailkeeper doctor` shows the catalog the scan judges by (revision, digest prefix, expiry and days left, rules by review state: a warning within 14 days of its expiry, for a catalog not valid yet and for approved rules whose review is not fresh, and a failure after the expiry, all by the predicates `Match` uses) and whether an intent set is configured, reading both by the scan's own code and making no request.
