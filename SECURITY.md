# Security

tailkeeper gives agents read access to a Tailscale tailnet, so a defect in it can expose that tailnet. Please report one privately.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting: the repository's **Security** tab, then **Report a vulnerability**. If the tab shows no form, open an issue that only asks for a private contact. Do not put details in an issue or pull request.

Include the version (`tailkeeper version`), the command or MCP call, what happened and what you expected. Leave out credentials, tailnet IDs, device names and addresses; if more is needed, you will be asked.

## What happens next

- An acknowledgement within 7 days.
- An assessment, and a fix or a plan for one, within 30 days of the acknowledgement.
- A fix ships as a patch release, with a line in `CHANGELOG.md` and a GitHub security advisory (and a CVE where one applies), crediting you if you want.
- Coordinated disclosure: please keep the details private until the fix is released, or for 90 days after your report, whichever comes first. If a fix needs longer, we will say why and agree a date with you.

## Safe harbour

Research done in good faith, on tailnets and accounts you own or are authorised to test, that avoids privacy violations, data destruction and service disruption, and that is reported as described here, is welcome. We will not pursue or support legal action against it. Do not test against tailnets you do not own.

## Supported versions

Only the latest release receives fixes.

## What counts

- Any path by which a credential, or an OAuth or JWT token, reaches tailkeeper's output, logs or audit log.
- Text from the tailnet (names, tags, comments, messages) that escapes the escaping, the size caps or the untrusted marking, or that a model is shown as tailkeeper's own words.
- A way past the tripwire that withholds key- and JWT-shaped output.
- Any way to change a tailnet through a release that is documented as read-only, including any API request other than GET, `POST .../acl/validate` and the credential's token request.
- An audit log that misses a call without the warning tailkeeper prints when the log is unavailable, or that records a value instead of metadata.
- With the default `"personalData": "mask"`, a login name, display name, email address, tailnet ID or public IP address returned whole in a field `docs/tools.md` lists as masked, or an email address or public IP address in other text from the tailnet or in the error message of a tool call, unless the field is listed as never masked. In the fields listed as having their email addresses masked (the policy text and `acl_test`'s reasons), an email address returned whole counts, and so does the ETag, size or SHA-256 of the unmasked policy.

Key- and JWT-shaped text in a result is always the tripwire's, so it is withheld or replaced; the `audit_log` preview cut is a best-effort one for every other shape, so a credential that shows through a shape listed under Known limits below is a known limit, and any other path still counts.

## Known limits, not vulnerabilities

These are known limits of the latest release. `tailkeeper doctor` reports some of them:

- Personal mode runs as your user: code that runs as you, including an agent with an unsandboxed shell, can rewrite tailkeeper's configuration and audit log.
- The configuration file and a `file` provider's credential file are read through the file that passed the ownership and permission check, not looked up by name a second time. On every platform tailkeeper takes an `lstat` of the path, runs the checks, opens the path, and refuses the read unless the open file is the same file as the one the `lstat` described and is a regular file with the mode, size and modification time the `lstat` reported. On Unix systems the checks are the owner and permissions of the file and of the directory that holds it (not of the directories above it), the open refuses a symlink, the same file means the same device and inode, and the change time must be the one the `lstat` reported too, because a file system may give a new file the inode number of one just removed (ext4 does). That narrows a swap race between the check and the read; it does not close it. The checks look the path up by name, separately from the `lstat` and from the open, not at the open file, so a process running as you or as root that swaps the file twice in between (a file that passes the checks in place while they run, the first file back before the open) can still get a file read that the checks never saw. Such a process could rewrite the file anyway, as the first limit says. On Windows the checks only refuse a path that is not a regular file (`tailkeeper doctor` warns that ownership and permissions are not checked), the open does not refuse a symlink, and the comparison of device and file index does not pin the file, because Go reads the identity of the `lstat` result by name when the two are compared; the kind, mode, size and modification time from the `lstat` are still compared with the open file (Go's `FileInfo` carries no change time on Windows, so none is compared).
- Some files are read by name, with no check of owner, permissions or directory, and a symlink is followed: any file that a `file:` value in a `TAILKEEPER_*` secret variable names (the credential, the privacy key or the OIDC token), and the token file of an `oidc` provider (`tokenFile`). Keep them mode 0600, in a directory only you can write.
- The audit log is a plain SHA-256 chain: it detects damage and naive edits, not a writer who recomputes the chain.
- On Windows the audit log has no lock between processes. The appends of one tailkeeper process are serialised in memory, so one MCP server's parallel calls keep the chain, but two tailkeeper processes appending at the same moment (for instance `tailkeeper doctor` while the MCP server runs) can write two lines with one sequence number. `tailkeeper audit verify` then reports a break although nothing was altered, and since `tailkeeper audit rotate` is refused on Windows, the way on is to stop every tailkeeper process and move the log aside; the new log is not linked to the old one. `docs/windows.md` lists the other differences of the Windows build.
- `tailkeeper audit verify` checks that the lines present chain correctly. It cannot tell that lines were removed from the end of the log, that the log was deleted and started again, or that an archive was deleted: a missing archive is reported as not checked, with a warning on standard error, and `audit verify` exits 0, because it cannot tell deletion from retention. A read whose line cannot be written (the lock held for more than 2 seconds, an unreadable log, a full disk) is not recorded, and tailkeeper warns on standard error. tailkeeper does not log its own start-ups or configuration changes.
- The value previews of the `audit_log` tool (the tailnet's configuration audit log; `includeValues`) are a best-effort cut, not a guarantee. Only an `http` or `https` URL is cut to its host, and only with its slashes written as `/`, `\/` or `\u002f` and its colon as `:` or `\u003a`: a URL with no scheme, with another scheme (`ftp://`, `slack://`), or with its slashes written another way (`%2F`, `\x2f`, a doubled backslash) is shown whole. Values under credential-named keys are removed (`true`, `false` and `null` stay), but a list of name and value pairs (`{"name":"Authorization","value":…}`) is not redacted, since its keys are `name` and `value`. Text in a string value that is neither JSON nor HuJSON (a truncated or doubled document, a document with other text before or after it, `key=value` pairs) stays as written. The pattern that recognises credential names also matches inside longer names (`tokenCount`, `secretary`), so it removes some values that are not secrets.
- Masking personal data is a best effort over text and has stated gaps: device names and hostnames are not masked as personal names are (an email address or a public IP address inside one is masked like any text), configuration fields such as DNS resolvers and routes stay whole, names written in free text and addresses in unusual forms are not found, and `acl_test` still confirms what a guessed user may reach until the ACL engine (M3) arrives. Pseudonyms appear in results only: an error message, or `acl_test`'s reasons, echoes what the caller typed, so it is masked without one, since a pseudonym beside a guess would confirm it. While masking is on, filters that would confirm a guessed value are refused (`filter_refused`), and `audit_log`'s digests of old and new values are keyed under the privacy key or left out without one. In the policy file only email addresses are masked: host names, tags, groups, SSH users, addresses and comments stay whole, and so does the name of a synced group, which is written like an address (`group:engineering@example.com`, after a space, a quote, an opening bracket or a separator; one with a space in it is masked from the space on, and a group is masked as an address when its name is quoted, escaped or holds `=` or `?`, when it is glued to the word before it, when it is written after //, or when it is followed by another address; an at sign written as `%40` or a JSON escape keeps the name whole). With a privacy key, a `[p:` that the policy holds, in a comment or a name, is shown with its bracket spelled out, so that a marker on the page is one tailkeeper appended.
- Masking reads email addresses written with `@`, its JSON escape and `%40`, with a quoted local part (`"amy"@example.com`, and `\"amy\"@example.com` in JSON text, become `a…@example.com`, with the pseudonym of `amy@example.com`: a quoted word, which may hold a space, is read back to its opening quote on the same line when it ends at the at sign or before a full stop of the local part, and an empty one, or one with no opening quote on the line, is not read, so `""@example.com` is shown as written; a quote of one kind closes a word that the other kind opened, so `\"amy"@example.com` also becomes `a…@example.com`), and IP addresses in their usual written forms. The name of a synced group (`group:engineering@example.com`, where `group:` begins a word) is left whole wherever masking runs, in the policy, in free text and in error messages, not only in the policy file. An address is read at the end of a run of hex digits, letters a to f, colons and full stops, however the run begins: right behind a label that ends in a hex digit or a letter (`ipv6:2001:db8::1`, `eth0:2001:db8::/48`), behind any name, word or number and a full stop (`eth0.203.0.113.7`, `a1.203.0.113.7`, `host-1.203.0.113.7`, `ipv6.2001:db8::1`), and behind a percent-encoded or backslash-escaped character (`%20203.0.113.7`, `%5B2001:db8::1`, `x\x52.94.236.248`). The digits after such an escape may be the escape's or the address's, so the text is read both ways, and masked if either reading holds a public address; a backslash and x or u is an escape even before a tailnet address (`\xfd7a:115c:a1e0::1` is cut). A public IPv4 address that ends a run is masked whatever precedes it, unless the run is one longer IPv6 address that is not public (`fe80:2001:4860:4860::8888` is a link-local address, and shown as written, with a colon and a port after it as well). An IPv6 address may end in `::` before full stops or colons (`2001:db8::.` becomes `2001:db8::/48.`), and may be followed by a port after a full stop, as tcpdump writes it (`2001:db8::1.443` becomes `2001:db8::/48.443`), or after a colon (`2001:db8::1:41641` becomes `2001:db8::/48:41641`, `2001:db8:::443` becomes `2001:db8::/48:443`, and `2001:db8::10.0.0.53:19` becomes `2001:db8::/48:19`). The run is read whole first, so a colon and up to four digits are one more group of the address where the two make an address (`2001:db8::1:4164` becomes `2001:db8::/48`), and the port only where they do not. An IPv6 address may also be followed by a full stop and a word or numbers, which the run of address characters takes in when they start with a letter from a to f or are digits (`2001:db8:abcd::9e8f.Error` becomes `2001:db8:abcd::/48.Error`, `2001:db8:abcd::9e8f.5.6` becomes `2001:db8:abcd::/48.5.6`, `2001:db8::1.dead:443` becomes `2001:db8::/48.dead:443`, and an address of eight groups before an IPv4 address or another address, `2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f.5.6.7.8` and `2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f.dead::1`, become `2001:db8:abcd::/48.5.6.7.0/24` and `2001:db8:abcd::/48.dead::/48`): when nothing else reads the run, and it holds no public IPv4 address to mask first, it is tried as ending before the first full stop after its last colon, and before the first after its first colon. A colon and a port before that full stop are cut off with it (`2001:db8:abcd:b3a7::9e8f:41641.example.com` becomes `2001:db8:abcd::/48:41641.example.com`). An address of eight groups has no `::` of its own, so it is cut before a port that follows `::` (`2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f::41641` becomes `2001:db8:abcd::/48::41641`) and before a full stop and a word or numbers that make no public address (`2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f.A0.0.0.0` becomes `2001:db8:abcd::/48.A0.0.0.0`). A tailnet or link-local address that is all there is to its run is shown as written with its port as it is without (`fd7a:115c:a1e0::1:41641`); behind a label that ends in a hex digit or letter, or behind an escape, the text before the address and its first groups can be read as another address, which is masked while the port stays as written (`dead:fd7a:115c:a1e0::1:41641` becomes `dead:fd7a:115c::/48:41641`, `ipv6%fd7a:115c:a1e0::1:41641` becomes `ipv6%fd7a:115c:a1e0::/48:41641`, and `\xfd7a:115c:a1e0::1:41641` becomes `\xfd7a:115c:a1e0::/48:41641`). An address of eight groups that ends its run, or that a port follows, is also cut after a prefix that ends in `::` (`peer::2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f` becomes `peer::2001:db8:abcd::/48`; with more groups after the eight the run is read as a whole, as the bullet on masking's errors says, and with a second `::` it is no address; and an address of eight groups, a full stop and a word or numbers, then `::` and eight groups more are two addresses, the front read first: `2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f.5.6::2606:4700:4700:1111:aaaa:bbbb:cccc:dddd` becomes `2001:db8:abcd::/48.5.6::2606:4700:4700::/48`), and when another is glued on in front of it with nothing between (`2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f` becomes `2001:db8:abcd::/482001:db8:abcd::/48`). An IPv4 address followed by colons is an address and the text after it (`8.8.8.8::443` becomes `8.8.8.0/24::443`), and so is a number after a slash that follows an address, whatever precedes the address (`1.1.1.1/8.8.8.8`, `eth0.203.0.113.7/8.8.8.8`, `%20203.0.113.7/8.8.8.8`), unless the slash follows text that ends in `.0`, as the networks masking writes do, or in `::` with a prefix length of 48 or 40: there the number begins with a prefix length (`10.0.0.0/8.8.8.8` is shown as written), which is read as the bullet on masked text below says.
- Masking reads a dotted number, which is numbers that single full stops join, for every four consecutive parts that make a public IPv4 address, wherever they sit in it. It reads a number of five parts or more, or of four whose first part is no octet, from the left: the first four parts that make a public address are masked by replacing the fourth with `0/24`, the count goes on after it, and the parts left over are shown (`203.0.113.7.443` becomes `203.0.113.0/24.443`, `8.8.8.8.1` becomes `8.8.8.0/24.1`, `1.2.3.4.5.6.7.8` becomes `1.2.3.0/24.5.6.7.0/24`). A part is an octet when it is at most 255 and has no leading zero; four parts that include a part that is not make no address (`8.8.8.256.1` and `8.8.008.8.1` are shown as written). A first part that is no octet stands for its last one to three digits, since a name's, an escape's or another number's digits run into it (`1238.8.8.8`, `ipv6.198.51.100.231`); behind an escape it stands for the digits after the escape's and for the longest octet it ends in, and for no other. Four parts that begin with 0 make no address, since 0.0.0.0/8 locates no one (`eth0.203.0.113.7` becomes `eth0.203.0.113.0/24`; `0.8.8.8.5` becomes `0.8.8.8.0/24`, because its last four parts are an address). A name that ends in another digit makes an address with the first three parts after it, and the window that holds both is cut at its third part (`ens5.203.0.113.7` becomes `ens5.203.0.0/24.7`).
- Masked text is read again, until it no longer changes and at most four times, because masking can make a new run of text (`123.` and the `8.8.8.0/24` that `::ffff:8.8.8.8` is cut to make a number that holds an address again). The prefix length after a network that masking wrote is its own (`203.0.113.0/24198.51.100.0/24` is two networks). After text that ends in `.0` a number begins with a prefix length of one or two digits up to 32, and what follows the prefix length begins the next number (`203.0.113.0/24198.51.100.231.443` becomes `203.0.113.0/24198.51.100.0/24.443`); two digits above 32 are no prefix length, and the number is read as an address (`1.2.3.0/88.9.9.9` becomes `1.2.3.0/24/88.9.9.0/24`).
- Masking does not recognise an address whose own colons or full stops are written as escapes (`2001%3Adb8%3A%3A1`), IPv4 octets with leading zeros after the first (`203.000.113.007`; zeros in front of the first are read as glue), an IPv6 address whose last group ends in the digits that an IPv4 address begins with (`2001:db8::a11.1.1.1` becomes `2001:db8::a11.1.1.0/24`: the IPv4 reading is the one masked), an IPv6 address that follows a colon and a full stop in its run and is followed by a full stop, a word and a colon (`a:b.2001:db8::1.dead:443`: its end would lie between two full stops), an IPv6 address followed by two full stops and a tailnet IPv4 address with digits glued on (`2606:4700:4700::1111..100.101.102.103100.101.102.103`: the kept address makes the run kept), an IP address written with dashes inside a host name (`ec2-203-0-113-7…`), or reverse-DNS names (`7.113.0.203.in-addr.arpa`, `b.d.0.1.0.0.2.ip6.arpa`), whose digits are read as the address they look like, not the one they spell. A run that holds two `::` is no address, and an address in it can be missed (`2001:db8::1::1100.101.102.1031.1.1.1` is shown with its first address, and only the last four parts cut). A run of dotted numbers after an address and a full stop is masked along with the address when it has six parts or fewer. A longer run can leave the address whole, and cuts only an IPv4 address that the run ends in: `2001:db8:abcd:b3a7::9e8f.710.0.0.10010.10.10.0` and `2001:db8:abcd:b3a7::9e8f.0.0.0.0.0.0.0.0` are shown as written, and in `2001:db8:abcd:b3a7::9e8f.10.0.0.256.0.0.0`, `2001:db8:abcd:b3a7::9e8f.10.10.10.10.10.8.8.8.8`, `2001:db8:abcd:b3a7::9e8f.0.0.0.0.0.0.0.0.8.8.8.8` and `2001:db8:abcd:b3a7::9e8f:41641:.0.0.0.0.1.0.0.0` only the last part is replaced by `0/24`. When a prefix and the first of the eight groups are a public address of their own, and a ninth group of up to four hex digits follows (a port, say), the prefix is cut and the address is read from its second group, so its second to fourth groups show (`dead::2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f:ab` becomes `dead::/48:db8:abcd:b3a7::/48`). An address of eight groups and a colon and a last group of five or more hex digits that are not all digits is shown as written, after a prefix too, since the last group is no port and no group of an address (`2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f:abcde` and `x::2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f:abcde`); five digits or more are a port (`2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f:41641` becomes `2001:db8:abcd::/48:41641`). It keeps an IPv4 address embedded in an IPv6 one (`64:ff9b::203.0.113.7`) when that literal is all there is to its run of hex digits, letters a to f, colons and full stops (a colon or full stop after it, a name and a full stop or a colon before it, or hex digits or an escape's digits before it make it part of a longer run, and the IPv4 address is masked: `dead64:ff9b::8.8.8.8` becomes `dead64:ff9b::/48`), and the keys of the two output maps that hold untrusted text (`customClaimRules` and metric labels, which hold claim and label names); text in those forms is shown as written.
- Masking also errs the other way, since a version or an identifier cannot always be told from an address: four dotted numbers that form a public address are masked (`6.5.0.14` becomes `6.5.0.0/24`), and so are four parts anywhere in a longer number (`v1.80.2.1.5` becomes `v1.80.2.0/24.5`, `1.2.3.4.5` becomes `1.2.3.0/24.5`, the OID `1.3.6.1.2.1.1.5.0` becomes `1.3.6.0/24.2.1.1.0/24.0`, a date written `2026.10.13.5.6` becomes `2026.10.13.0/24.6`), because a name, a full stop and an address (`eth0.203.0.113.7`) look the same. So is a private address next to an escape that its digits make public (`%2210.0.0.53` becomes `%2210.0.0.0/24`), and so is a private or tailnet address that shares a part with a public window (`ipv6.100.101.102.103` becomes `ipv6.100.101.0/24.103`, `1.2.3.100.64.0.1` becomes `1.2.3.0/24.64.0.1`). So is a run of colon-separated numbers that ends in a number after the eight groups of an address, whatever else it is (`dead:1:2:3:4:5:6:7:8` becomes `dead:1:2::/48:8`: the first eight groups are the address and the last number its port). So is a run of sixteen groups, which is read as one address of eight with the second eight after it, and cut to the first eight's network, so the second address is hidden too (`2001:db8:abcd:b3a7:c9d1:e2f4:a5b6:9e8f:2606:4700:4700:1111:2222:3333:4444:5555` becomes `2001:db8:abcd::/48`). Device names and hostnames are not masked as personal names are, though an email address or a public IP address inside one is masked like any text, and filters and lookups on a name read what a result shows.
- The secret tripwire is a backstop that recognises two shapes only: a Tailscale key (`tskey-api-`, `tskey-auth-`, `tskey-client-`, `tskey-scim-`, `tskey-webhook-` or `tskey-app-`, in lower case) and a JSON Web Token written with all three segments (`eyJ` and ten or more characters of `A-Z`, `a-z`, `0-9`, `-` and `_`, a full stop, the same again, a full stop, and ten or more characters). It does not catch any other credential format (another vendor's key, a password, a signing secret, an OAuth client secret without the `tskey-client-` prefix, a token without a signature), which the typed output allowlist keeps out of results and the tripwire cannot.
- Errors raised before a tool runs (an unknown command, a mistyped flag, an unknown MCP tool name) repeat what the caller typed, escaped but not masked; they hold no text from the tailnet.
- Pseudonyms are deterministic: the same value has the same pseudonym every time. A tailnet member who can write free text the agent reads (a device or target name, say) and can see the agent's output can therefore plant a guess at someone's address and compare the pseudonym that appears beside it with another. That is inherent to stable pseudonyms; it is why the privacy key must stay secret, and why a pseudonym is shown only for values tailkeeper masked itself. A pseudonym-shaped marker shown in `acl_test`'s reasons, or in a field kept unmasked as configuration, was not necessarily written by tailkeeper, since only masked free text and the policy text of `acl_get` have forged markers rewritten.
