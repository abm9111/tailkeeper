# Changelog

What each release of tailkeeper changed. Versions follow semantic versioning; until 1.0, a minor release may change the CLI or the MCP tool list.

## 0.6.0 — unreleased

Upgrading: some exits and codes of commands that already exist change, and a script that reads them should be checked against this list. A command given a bad argument and a bad configuration exits 2 where it exited 6. `acl test`, and `doctor --probe` which runs it, exit 1 with `validate_rate_limited` once they pass 30 validation requests a minute (`acl.validatePerMinute`), where nothing limited them; the error carries `retryAfterSeconds`. A failure to inspect the configuration file is `config_unsafe` where it was `config_invalid` (both exit 6). A privacy key file that cannot be read, is unsafe or does not parse is `privacy_key_unavailable` (exit 5), where it was `config_unsafe` or `config_invalid` (exit 6). `acl get` of a live policy over 4 MiB fails with `api_error` (exit 1) that names its size, where it showed a policy of any size it could read. A text flag or a positional argument over 8 KiB is a usage error (exit 2). The two new configuration keys are refused by a 0.5.0 binary (`config_invalid`, exit 6), so a configuration that a 0.5.0 binary also reads cannot use them.

### Added

- `--fail-on` refuses, before anything loads, a kind that the command does not compute: a result type can say which kinds it fills (`registry.Computes`), and the usage error names the token and lists the ones the command does compute. A gate on a count that is always 0 never fires, and a pipeline that relied on it stayed green. A result type that says nothing takes all five tokens, as before. `acl diff` says that it computes four (it has no `warnings` to count), and `acl validate` that it computes all five and, with `--offline`, none.
- Binder rules for the policy commands, which `acl validate` and `acl diff` use (the 8 KiB limit on a flag value is not among them: it is checked on the tool commands only, see Changed). A file field can be filled from the first or the second argument (`OLD NEW`, as if its flag had been typed), and the usage line names them. The command line marks its call as the operator's own (a field MCP can never set), so that a policy file the operator names is told from policy text an agent sends. In a tool that reads files, every text field that no file fills must say `tk:"short"` (a name, a token, an identifier) or the tool does not build, so a document cannot become a flag.
- Library code for files that hold policy content: `safefile.Options.Verify` runs a check on the file that was opened before a byte is read, and `config.OwnedBy` is the check that holds a file and its directory to the rule the configuration file gets (owned by the user, writable by neither group nor others). The invariants file is read through both.
- Library code for pseudonym subjects, which `acl_validate` and `acl_diff` use: a resolver that turns a pseudonym into the one user it names (`GET /users`, held for one call), a reverse map that masks a resolved login, and any word glued to it, out of Tailscale's reply, and the subject rule over a policy text and over patch operations.
- `TestMaskingScalesLinearly` also times some rows of the guard (the email scan and the colon scan) from 128 KiB to 1 MiB, and the bound on the work of `sanitize.String` is tested by bytes allocated, not by its output (#13).
- Fuzzing runs nightly one package to a job, with the inputs a night finds carried to the next, so a long package cannot time out the others. `make fuzz FUZZ_PKG=./internal/acl` fuzzes one package, and `FUZZ_MIN` is the number of targets that must run. The pull-request job named `fuzz` is unchanged.
- `make mutate` changes a package's code one listed mutant at a time (the `mutants.txt` beside the package; `MUTATE_PKG` picks one package) and fails if a test does not notice. It is not part of `make verify`.
- `make cover` also requires 95% statement coverage for `internal/acl` and `internal/guard`, measured from each package's own tests.
- `make probe-acl`: the owner's live probes of the policy validate endpoint. It sends about 50 documents to `POST .../acl/validate`: synthetic ones, or ones built in memory from the tailnet's own policy and sent back to its own validate endpoint, which changes nothing. It makes up to ten reads, the policy and the configuration audit log (that read needs the `logs:configuration:read` scope), through the read client, and prints what the API answered without printing a value from the tailnet: statuses, key paths with their JSON types, and error texts reduced to templates in which only the grammar's own words survive. It writes one skeleton file per probe for the owner to commit. It is opt-in (`TAILKEEPER_LIVE=1`, which the target sets), not part of `make verify`, the target is never run in CI (a test builds the tagged binary only to prove that it stops without a configuration and sends nothing), and the command is not in any release: it exists only in a binary built with `-tags probe`.
- `internal/api`: `ValidatePolicy` and `GetPolicy`, the low-level calls the probes use (one attempt, any status returned as data). The fake API in `internal/api/apitest` gains a shape ledger (`Documented`, `Observed`, `Assumed`) that every test must use for validate and details answers, and a spy that fails a test whose validate request names one mode and carries the other's body.
- `docs/scopes.md` and `tailkeeper scopes` have a column for scopes a tool uses for one feature only, and `tailkeeper scopes --json` an `optionalTools` key for them; `tailkeeper doctor` reports a missing optional scope as information, not as a failure.
- `tailkeeper acl test --quiet` prints nothing when the test passes (exit 0). The command line also gains the exit policy that the policy commands use: `--fail-on` (comma-separated, repeatable: `warnings`, `tests-reduced`, `defaults`, `widening`, `change`) turns findings into exit 8, `findings_present`, and never hides exit 1, 9 or 2. `acl validate` and `acl diff` offer it, each with the kinds it computes.
- The command line gains `--format text|json` for results that have a human layout: `text` is the default, and `json` is the same as `--json`. `tailkeeper acl validate` and `tailkeeper acl diff` offer it. The text layout prints a verdict, what was not checked, counts by class and located findings (`file:line:column:`), with Tailscale's own text behind a notice; it uses colour only on a terminal with `NO_COLOR` unset.
- `--format github` and `--format markdown`, for the commands whose results have a human layout, which are `tailkeeper acl validate` and `tailkeeper acl diff`. `github` writes one workflow annotation for each finding, at most ten of each severity and then a line saying how many were left out, with the data and the properties escaped as GitHub requires and a `file=` only for a path inside the repository, written from its root with forward slashes: the command reads `GITHUB_WORKSPACE` for the root, an absolute path inside it is written relative to it, and a path outside it is left out and its location goes into the message instead. The warnings the live policy already has are notices marked `existing:`, not warnings, so that they take none of the ten warning annotations a new warning needs. The annotations are the only lines that reach the runner without the CI-log guard; every other line is indented and guarded, because a runner trims leading white space and a group name must not be able to write `::add-mask::` or `::stop-commands::`. The formatter reads no environment variable and opens no file, so nothing reaches `$GITHUB_OUTPUT` or `$GITHUB_STEP_SUMMARY`. `markdown` is for step summaries and pull request comments: text is escaped, or put in a code span when it is Tailscale's, so that it cannot mention a person, link an issue (`#12`, `GH-12`) or an address, or open HTML. A fuzz target holds the property for the first (`FuzzGitHubFormatter`; `make fuzz` runs eleven targets and the nightly job fuzzes `internal/cli`).
- Two configuration keys: `acl.invariantsFile` (the invariants file every policy validation also checks) and `acl.validatePerMinute` (the validation requests one process decides to send per minute, 1 to 120, default 30; a retry of a request takes no token). `acl_validate` checks the invariants file `acl.invariantsFile` names on every validation, and a bad value is refused when the configuration loads. `acl.validatePerMinute` sets the limit that `acl_test` and `acl_validate` are held to (see Changed). A 0.5.0 binary refuses both as unknown keys (`config_invalid`, exit 6, for every tool), so set them in a context only 0.6.0 uses.
- A new error code, `validate_rate_limited` (exit 1), and a field `retryAfterSeconds` in the JSON of an error: the whole seconds to wait, rounded up and at most 86400 (24 hours), set on `validate_rate_limited` and on the `api_rate_limited` error of a 429 whose `Retry-After` named a wait (a `Retry-After` of 0 leaves it out).
- `acl_get` gains `view: summary` (`tailkeeper acl get --view summary`): the sections the policy writes with their state and size, the values of the scalar ones, the names it defines in `groups`, `tagOwners`, `hosts`, `postures` and `ipsets`, the groups it refers to that it does not define (synced from an identity provider), the number of `tests` and `sshTests`, and the sections this version does not know, with no policy text. With a privacy key it also carries a keyed digest of the names and one of what the policy means (`semanticDigest`: equal after a reformat or a rewrite of `acls` into `grants`). Each list shows at most 100 names of at most 256 bytes, within a budget that keeps the result under the 200,000 characters the tool declares; `namesTruncated` says a list was cut. `fromLine` and `toLine` are 0 in this view.
- `acl_get` also returns `warnings` and `serverErrors` (Tailscale's own, about the policy as stored: at most 64 of each and at most 16,000 characters of each as JSON text, so that with the default page of the text view, or with the summary, the result stays under the 200,000 characters the tool declares (a `maxBytes` page of up to 4 MiB is the caller's choice and can be larger); the last entry of a list counts the messages left out; addresses masked with no pseudonym beside them), `policyVersion` (a keyed digest of the ETag with a privacy key, the ETag itself with `personalData: show`, nothing otherwise: the ETag is the unkeyed SHA-256 of the file, so while masking is on it would confirm a guessed address) `policySha256`, which is the value `sha256` already held, and `checkedAt` (when the policy was read, RFC 3339 in UTC, as `acl_validate` and `acl_diff` say it), in the text view and in the summary and so in `tailnet://acl`. All of these are additions.
- The resource `tailnet://acl` serves the summary above. A read makes one request for the policy and one for the settings, is audited as a resource read and waits for a free slot like any call.
- The server's instructions name the order of work with a policy: the summary first, a pseudonym from `users_list` when a person is involved, then `acl_test`, `acl_validate` with a patch and `acl_diff`, and that an agent proposes a change by validating a patch and the owner applies it.
- `acl_validate` (`tailkeeper acl validate [--from FILE|- | --patch FILE|-] [--offline] [--fail-on KIND] [--format text|json|github|markdown] [--quiet]`): asks Tailscale whether a policy is valid, the proposal you give or, with none, the live policy (`validatedLive` says so: an empty policy is no policy), and answers with a status: `pass` (exit 0), `unknown` (1, never a pass), `invalid`, `rejected` or `unresolved` (2), `fail` (9). The text goes to `POST .../acl/validate` exactly as written, comments and trailing commas kept, and nothing on the tailnet changes. A test that failed is told from a test that names something Tailscale cannot resolve by the shape of the message, never by a word in it; a warning is existing only if the live policy already has it word for word, as its text or as the policy element it names, a colon and its text (a warning that Tailscale words differently from the one stored reads as new, the side a gate wants); a pass is `unknown` if the live policy changed during the check. A rejection or a failed test is placed in your text: the line and column when Tailscale gives one, every place that holds a quoted name when it does not, never one guessed line. `changes` counts the differences from the live policy by class (`--fail-on change` counts the entries that changed, a widening with the rule it belongs to), a text that is the live policy byte for byte has no new warnings, and a live policy that Tailscale stored with errors is `rejected` without being sent, and the verdict says so (a patch or a proposal against it is sent, and `serverErrors` still lists them). A call takes one token of the validation bucket, a 500 is retried once (its error names the digest of what was sent, not the text), and a reply is read up to 64 entries of 64 messages. A result carries at most 64 problems whichever way they came (a reply, a text of thousands of unknown sections, the live policy), errors first, and `omitted` counts the rest, which every layout says. Every warning of a reply is classified as new or existing, the ones past those 64 entries too: a new warning the lists do not show is counted in `newWarningsOmitted`, and `--fail-on warnings` fires on it. A change is proposed as a patch (RFC 6902 operations, `patch` over MCP), applied to the live policy with its comments and layout kept: `acl_get` shows a masked copy that cannot be sent back, so an agent edits by patch. A user is named in a proposal or a patch only by the pseudonym a result showed (`p:...`, or the masked value that carries it); tailkeeper reads the users, with the optional `users:read` scope and only when a pseudonym is given, and replaces it by the login in the request, which no result, error or audit line repeats. Over MCP a text that holds a credential shape is refused before anything is sent (JSON escapes are decoded first, since Tailscale decodes them), and so is one that adds or replaces more than 64 tests, counted on the policy a patch makes as well as on its operations; a file the operator names on the command line is sent as it is. A patch over MCP may not hold an RFC 6902 `test` operation (`acl_diff` reads patches the same way): it compares a value the caller cannot see, so whether it holds would confirm a guess at a value that masking hides, as often as the API answers; the result is `invalid` and names the operation, and a patch file the operator names keeps it. A line and column in a result are those of the text you wrote (for a patch, of the patch you wrote), not of the text with the logins in it. Two kinds of text hold logins you never saw, and a result gives no column for them: a problem in the live policy has its line (the line `acl_get` shows) and no column, and a problem in the policy a patch makes is placed by a JSON pointer and has no line, and Tailscale's own "line N, column M:" for it is left out of its message. A number that would depend on how long a login is does not reach a result: a text that names users by pseudonym is refused when it could come to more than the 4 MiB tailkeeper reads with every pseudonym replaced by a login of the longest size, so that where a text is refused tells nothing of the logins, and the engine's messages about a text that is too large no longer say how long it is. `patchedBytes` is the size of the patched policy as `acl_get` shows a policy (the masked text while personal data is masked), never the file's own size, and `patchedDigest` is the keyed digest that `acl_get`'s summary should show once the owner has applied the change (that depends on how Tailscale stores the policy, which has not been observed). The invariants the owner keeps (`acl.invariantsFile`, a HuJSON object with `tests` and `sshTests` and nothing else, a regular file owned by the user who runs tailkeeper, in a directory owned by that user, and writable by no one else (on Windows only the regular file is checked); `--invariants FILE` replaces it on the command line and `--no-invariants` removes it) are checked on every validation, the live policy's included, by a second request: the same text with its own tests taken out and the invariants put in, so that a failure is attributed to the invariants and is placed at its line in the invariants file. The second request carries a canary, a test that fails whatever the policy allows, and the answer must contain its failure once: a clean pass, a missing canary or one that is unevaluable is `unknown`, never a pass. A call with invariants takes two tokens of the validation bucket, and the second request is skipped, and its token given back, when the first was not accepted or not read; a file that holds no tests sends one request (a notice says so). `--invariants` and `--no-invariants` together are refused. `invariantsApplied` is the number of invariant tests in the second request once its canary came back (a test that could not be evaluated is among them, and makes the status `unresolved`), 0 when they were not run, and `invariantsSignature` is always `none`. A set path that cannot be read is `config_invalid`, and a file or directory with the wrong owner or mode is `config_unsafe` (both exit 6), on every call that uses it. When a test of the policy failed and the invariants then gave no clear answer (the canary did not come back once), the status is `unknown` (exit 1) and not `fail` (exit 9): `unknown` is the more severe of the two, and the failed tests are still in `errors`. `--offline` checks the text here only (encoding, syntax, structure, the sections tailkeeper knows), needs no credential, and says in its verdict that nothing was sent to Tailscale: it is `pass` with exit 0 and `serverChecked: false`, so a script that gates on `status` alone reads it as validated and should test `serverChecked` as well. Without `--offline` a missing credential is `credential_unavailable` (exit 5), never a local result. The first line of the report counts what Tailscale said (its messages, the assertions that failed), not the places a message is filed at, and names the new warnings that were cut from the lists. A file or standard input that is empty is refused (exit 2) on every file flag of the policy commands, `acl diff`'s too: an empty text is not a policy, and it would otherwise read as no text and validate the live policy. Over MCP the tool is open-world with a title, a user may be named only by pseudonym (a literal login is refused while personal data is masked), and every verdict is a typed result. A new error code, `too_complex` (exit 2), for a policy past the engine's size or work budget.
- `acl_diff` (`tailkeeper acl diff [OLD [NEW]] [--against FILE|live] [--from FILE|-] [--patch FILE] [--section NAME] [--from-change CURSOR] [--ignore-tailscale-written] [--offline] [--fail-on KIND] [--format text|json|github|markdown] [--quiet]`): compares two policies by what they mean and lists the changes by class, `defaults`, removed tests and widenings first, then the constructs Tailscale writes itself, then the rest. A comment, a layout, a key order, `acls` written as `grants` and a rule split or merged are no change. The old side is the policy in `--against` or the live policy; the new side is `--from`, or `--patch` applied to the live policy, or the live policy; both sides live is refused. `acl diff OLD NEW` compares two files and needs no credential, and `--offline` refuses a live side. Nothing is sent to Tailscale for validation, so the tool is not open-world. Over MCP the texts follow `acl_validate`'s rules (a user only by pseudonym, no credential-shaped name, no test operation in a patch, no cap on the tests a text holds, since nothing is sent) and every string of the result, the live side's and a text's alike, is masked as `acl_get` shows it, with a marker a policy spells itself rewritten and a login that a pseudonym stood for hidden whole (an operator's own file is masked with no pseudonym beside it). What a note says is one of a fixed list of sentences: it never quotes the policy, and the destination a wide source is new for is in `fields`. A string is cut at 1 KiB after it is masked, so where it is cut tells nothing of how long a login is; a page lists at most 50 changes and stops at about 56,000 characters as a host receives them, a list of members gained or lost at about 6,000, and a side's findings at 64 and 26,000, so that the result stays under the 200,000 characters the tool declares. `nextChange` continues a page and `section` narrows it, while the counts, the status and `--fail-on` cover every change: a section that selects nothing is `changed` still, and the layout says that the filter selected nothing. A side lists at most 64 findings and `omitted` counts the rest. `--fail-on` takes `tests-reduced`, `defaults`, `widening` and `change` here; `change` fires for any of the five classes and counts the entries that changed, not the classes added up (a widening is counted with the rule it belongs to, so one widened rule is `change (1)`), Tailscale-written ones too unless `--ignore-tailscale-written`, a flag for a drift job that compares the live policy with a file (a Funnel attribute a person added reads `equal` with it), not for a pull-request gate. `nextChange` is a digest of the two policies as the result shows them, of the section and of the Tailscale-written option, keyed with the privacy key when there is one: it identifies the comparison it was issued for, tells nothing that `policySha256` does not (two live policies whose logins differ and are shown alike give one cursor, as they give one digest), and is refused for another comparison. `equal` and `changed` exit 0, `invalid` (a side is not a policy) 2. `notChecked` says what a diff does not establish: a small change to an alias or a group can widen access.
- A policy file saved the way Windows PowerShell 5.1 saves one is refused before anything is sent, with the way out: a UTF-8 byte order mark and UTF-16 are `invalid` (kind `encoding`, at line 1, column 1) and the message says to save the file as UTF-8 without one. Lines are counted by line feed and columns in bytes, as Tailscale counts them, so a file with CRLF line ends reports the same line and column as the same file with line feeds only, and the human layouts add a notice that says so. A path is printed as it was typed, a space included, in the text, in a GitHub annotation and in Markdown. Tests hold all of this on files that keep their bytes.

### Fixed

- Built with Go 1.27.3: Go 1.27.2's `crypto/x509` trusts compromised intermediate certificates (GO-2026-6809), which reaches tailkeeper through its TLS connection to the Tailscale API.
- A credential file that is not there is named, with what to create: `credential_unavailable` (`privacy_key_unavailable` for the privacy key) says "the credential file ... does not exist" and to create it with mode 600, where it said it could not read the file. A line of a credential file over 64 KiB is `config_invalid` and names the line, where the scanner's own message came out. A privacy key file that cannot be read, is unsafe or does not parse is `privacy_key_unavailable`, with the reason and the fix (exit 5, where it was 6), and no longer `config_unsafe` or `config_invalid`. The `file` provider takes off one matching pair of quotes round a value, where it took off any run (`K='abc"` is now `'abc"`). An OIDC token file with nothing in it says so.
- On Windows, the configuration file and a `file` provider's credential file are read through the file that was inspected. The comparison of the open file with the earlier `lstat` read both identities by path afterwards, so a file put in the path's place compared equal to itself and was read. It is now the comparison a policy file gets: the volume and index are read from a handle that does not follow a reparse point when the file is checked. On Linux and macOS, a file put in the path's place with the same size, mode and times but another owner or group is refused too.
- The release notes now come from this file. `.goreleaser.yaml` disabled GoReleaser's changelog stage, which is the stage that reads the notes the release job cuts from this file, so 0.5.0 was published with only its footer. The stage stays on. A test fails if it is disabled while the release workflow passes the notes, and `make release-check` and the manual snapshot run now run the release path with a notes fixture and fail unless GoReleaser read it.
- The release workflow verifies the cosign signature of `checksums.txt`, as the README tells a reader to, before it publishes a draft release.
- Masking leaves the name of a synced group, `group:engineering@example.com`, as written and names nothing for it, where `group:` begins a word (at the start, or after a space, a quote, an opening bracket or a separator). A group is masked as an address when its name is quoted, escaped or holds `=` or `?`, when it is glued to the word before it, when it is written after //, or when it is followed by another address; an at sign written as `%40` or a JSON escape keeps the name whole. It had been shown as `group:e…@example.com`, which made two groups with one initial look alike.
- Masking hides a quoted local part (`"amy"@example.com`) when a control character stands between the closing quote and the at sign, whether the character is a raw byte, `%01` or a brace escape such as the one `acl_get` writes for a control character. The quoted name had been shown.
- The pseudonym of an address that text glues to a word with `=` or `?` (`user=amy@example.com`, `?u=amy@example.com`) is the address's own, as `users_list` shows it. It had been the pseudonym of the whole run, so a filter given it matched nothing. A login whose local part holds `=` or `?` (`a=b@example.com`) is named in text by the part after it.
- A login or display name that the API returns and that holds a backslash sequence is no longer given the pseudonym of the address the sequence spells. Pseudonyms of values from the API decode no JSON escapes; text from a policy or free text still does.
- With a privacy key, `acl_get` shows a `[p:` that the policy itself holds with its bracket spelled out, as free text does, so a marker on the page is one tailkeeper appended. `masked` is true for a page whose only change is such a marker.
- `sanitize.String` and `Text` return at most the limit they are given: below 14 bytes they returned the 14-byte truncation notice. `HasTag` finds no empty option in an untagged field. Nothing called either with such arguments.
- `--json` prints a JSON error on every error path of the command line: a bad global flag, a mistyped flag, an unknown command or area, a failed start of the credential wrapper, and the flag errors of `docs`, `scopes`, `doctor` and `audit`. `version` prints JSON when `--json` comes before the command (`tailkeeper --json version`), `audit verify` and `audit rotate` print JSON under `--json`, and `scopes` takes `--json` after the command. A `--json` anywhere on the line counts, also after an unknown command or a bad global flag. `docs --check` of a stale file is the same error form (exit 1 as before), and `doctor` says on standard error when its report cannot be printed. A mistyped flag no longer prints the list of every flag. (#8)
- A `--` that a flag takes as its value (`devices routes --context -- web-1 --json`) no longer ends the flags. (#8)
- A stale `TAILKEEPER_REEXEC=1` is named in the credential error, which says to unset it if no wrapper ran, and the fix for a missing credential names the variables to set. `docs --check` of a missing file no longer points at `make docs`. `tailkeeper local lock-status` no longer prints `nodeKeySigned: unknown` while the lock is off. `doctor --probe` no longer tells its reader to run `doctor --probe`. `docs` and `doctor` exit 1 when they cannot write their output. The usage text names `--context` and `--json` where they apply. (#8)
- The command line no longer passes CI log commands through: its text and its `--json` output, on standard output and standard error, are written so that a line cannot start a GitHub workflow command (`::`, after white space) or an Azure formatting command (`##[`), and no line carries an Azure logging command (`##vso[`) or a TeamCity service message (`##teamcity[`) anywhere. In text the first character is written as an escape; in JSON the first `#` of `##vso[` and `##teamcity[` is written as the JSON escape for `#`, so the output is still valid JSON and decodes to the same strings. This covers results, errors, usage text, `doctor`, `audit` and warnings. The MCP server's output is not a CI log and is not changed.
- On Windows, a path with the `\??\` prefix (the NT namespace) is refused like one with `\\?\`. A device reference longer than 253 bytes is refused even when it looks like a node ID. A tool whose input field takes a flag the command line registers itself (`--json`, `--context`, `--format`, `--quiet`, `--fail-on`) is reported as an internal error, with `--json` honoured wherever it stands, instead of panicking.
- `docs/tools.md` says "1 tool." for a registry of one tool, and says a tool may send only some of the API operations listed for it. `docs/design.md` now says an unsafe credential file fails the API tools only, and that the API client honours `HTTPS_PROXY`.
- A `Retry-After` of billions of seconds, or of more digits than any integer holds, no longer overflows into a negative wait or is dropped as if the server had sent none, which made the client retry after half a second: a count of seconds of any length is read, up to 24 hours, and the client then waits at most 30 seconds before each retry (a validation call also ends at its own 60 second deadline). (#12)
- A response one byte over the size limit is refused. The API client had accepted a body that was one byte too long when the JSON value in it ended before the last byte. (#12)
- The API client forgets the scopes it remembers for a token when a refresh of the token omits the `scope` field, where the earlier token's list stayed in force. (#12)

### Changed

- A text flag (a string, or a list such as `--fail-on`) or a positional argument of a tool command (`acl test`, `devices get`, and every other command that runs a tool) longer than 8 KiB is refused with a usage error (exit 2) that says how long the value was and does not repeat it: a value that size is a document, not a name, and the standard flag package would have echoed all of it in its own message. A document goes in a file or on standard input, not on the command line; a command that reads files names its file flags in the message. The check does not reach the other flags (`--context`, the boolean flags, a flag name), the arguments of the commands that are not tools (`doctor`, `audit`, `scopes`, `docs`), or the error the flag package raises for a bad flag: those errors repeat the value, cut to about 1 KiB.
- A failure to inspect the configuration file or a credential file that exists is `config_unsafe` (exit 6) in `Load` and in `ReadSecretFile` alike; `Load` said `config_invalid` for the configuration file (also exit 6). The linter excuses gosec in test files only for the rules that fire on fixtures (credential-shaped names, file modes and paths, subprocesses of the test binary, seeded generators); any other gosec rule applies to a test file.
- On Windows, a reparse point at the path of the configuration file or of a `file` provider's credential file is refused (`cannot inspect`, with the reason): a symbolic link, a junction, and a OneDrive Files On-Demand placeholder are all reparse points, and the file was read through them before. If the file is one of these, keep a local copy of it outside the synchronised folder and point the context at the copy.
- The pin of Tailscale's OpenAPI document (`internal/api/openapi`) is refreshed to the document of 18 Oct 2026. It differs from the pin of 12 Oct by one response field, `adminConsoleSessionTimeoutMinutes` on the tailnet settings, which `settings_get` does not return. The pin now also records the parameters and request content types of every read operation and of the validate call, and the error fields of the validate call, so a change to the `details` parameter of the policy file or to the content types of the validate call fails the weekly drift check.
- The weekly drift check retries its download of the document three times.
- The manual snapshot run of the release workflow builds in a job of its own that holds read access only.
- `docs/design.md` states the contract of 0.6.0, the read side of the ACL engine: the tools, the rules of the engine, the error and exit codes, the tests, and the live probes whose results decide what is still open.
- `acl_test` is advertised as an open-world tool with a title, and its description says the test is sent to Tailscale: it was always sent to `POST .../acl/validate`, and hosts that trust `openWorldHint` can now see it.
- An error raised without a hint of its own carries a generic one for its code, written for a program: what to do about it, and whether retrying can help. A test fails for an error code without one.
- The command line checks a tool's arguments before it loads the configuration and before it starts the `exec` provider's wrapper, so a value the tool refuses (`acl test` with no destination, a `--limit` out of range, a malformed ID) no longer costs a secret-manager unlock. Such a refusal is not recorded in the audit log, like any other usage error: nothing was read. A bad argument now wins over a configuration problem: a command with both exits 2 where it used to exit 6. (#8)
- Validation requests are held to a limit of tailkeeper's own: `acl.validatePerMinute` a minute (default 30) for the process, at most two validation calls at once, and 60 seconds for one call. `acl_test` and `acl_validate` are counted, and so is `doctor --probe`, which runs `acl_test`; a call past the limit fails with `validate_rate_limited` (exit 1) and says how long to wait, in `retryAfterSeconds` and in the message ("try again in N s"), which the text a command prints carries. The bucket holds at least two tokens, however low the key is set, because a validation with invariants takes two at once: at 1 a minute it starts with two and refills one a minute. The limit counts the validation requests tailkeeper decides to send, not the attempts: a retry of a request takes no token, so an upstream that keeps failing can see up to four POSTs for each token, within the call's 60 seconds. The key had been read and validated, and nothing used it.
- `acl_get` reads the policy with one request, `GET .../acl?details=true`, where it read the plain text: the text, the warnings and the version come from one answer. Both forms need `policy_file:read`. A policy over 4 MiB decoded is refused with its size. `tailkeeper acl get` prints the warnings, the stored errors and the summary one fact to a line behind a notice that the text is Tailscale's, and prints no document when there is no text.
- The help line of `--fail-on` lists the kinds the command computes: `tailkeeper acl diff --help` no longer offers `warnings`, which it never counts and refuses. A command that does not say lists all five, as before. `acl validate --offline --fail-on KIND` is refused too (usage error, exit 2, naming the kind and `--offline`): an offline check compares nothing with the live policy and sends nothing, so no kind can be computed, and a gate on one would never fire. `acl diff --offline` compares two files here and gates on its four kinds as before.
- `make test`, `make cover` and `make cover-pkg` give `go test` 300 seconds where they gave 180: the slowest package under `-race`, `internal/tools`, takes 80 s on an idle machine, and a timeout panic on a busy one reads as a failing test. CI already gave the suite 300 s on Linux and 900 s on Windows.
- The byte budget of the tool list (`toolListBudget`, the size of the tool definitions an MCP host loads) rises from 65,536 to 90,404 bytes: `acl_get` gains the input `view` and an output schema for the summary, `acl_validate`'s result schema describes a problem four times (errors, notices, new and existing warnings) and takes a patch, `acl_diff`'s describes a change and, for each of two sides, a problem, and the descriptions of the two tools name the refusals an agent would otherwise learn by meeting them. The budget is a decision a change takes, so it is raised here and the reason is this line.

### Fixed

- Masking finds email addresses written with `%40`, with a quoted local part (`"amy"@example.com`), and with quotes that split a percent-encoded at sign (`%4"0amy"@example.com`). It also finds one with a control character, or a brace escape such as `\u{0001}`, in its local part or right after the at sign. Reading a quoted local part takes time linear in the text.
- Masking finds an IPv6 address behind a label that ends in a digit (`ipv6:2001:db8::1`), before a full stop and a word (`2001:db8::1.Error`), and before a port after a colon or a full stop (`2001:db8::1:41641`, `2001:db8::1.443`), also when a full stop and more follow the port (`2001:db8::1:41641.example.com`). An address of eight groups is found before `::` and a port, before a port and `::`, and before a full stop and a word.
- Masking finds a public IPv4 address behind a name and a full stop (`eth0.203.0.113.7`), behind an escape (`%20203.0.113.7`), at the start of a longer dotted number (`203.0.113.7.443`), and after a slash that follows an address (`1.1.1.1/8.8.8.8`). Masking is a best effort: SECURITY.md lists the forms it does not read.
- The invite tools no longer return the tailnet ID.
- `audit_log` cuts each `http` or `https` URL it can read to its host and a hash of its path, in a target's name and property, in action details, in an error and in `includeValues` previews, also when `personalData` is `show`; `log_streaming_get` does the same to a URL in a delivery error. A token in the path of a webhook or log-stream URL no longer shows. SECURITY.md lists the spellings of a URL that stay whole.
- `audit_log` previews remove the values under credential-named keys (`true`, `false` and `null` stay), also in a policy file held in a string: HuJSON (comments, a byte order mark, trailing commas) is read before redacting. Text that is not strict JSON and nests more than 1,000 levels deep is removed rather than parsed, so a deeply nested value cannot exhaust the stack. SECURITY.md lists what this cut does not reach.
- `audit_log` shows a target's `property` as untrusted text, as it does the target's name: escaped, capped, masked, and with credential shapes replaced.
- A webhook or log-stream URL that is set and cannot be read shows as a URL that could not be read, not as an empty host.
- `devices_list`'s `nameContains` filter and the lookup of a device by hostname (`device_get`, `device_routes`, `device_posture_attributes`, `device_invites_list`) read the name as the result shows it, so they cannot confirm a guess at an address the result masks.
- The configuration file and a `file` provider's credential file are read through the file that passed the ownership check, not looked up by name a second time: on macOS and Linux, a file put in its place in between is refused (also one that takes the inode number of the file removed, as ext4 gives it), a symlink there is refused too, and a FIFO cannot block the read. That narrows a race and does not close it; SECURITY.md says what is left.
- A credential's secret (an OAuth client secret or an API key) no longer prints under any format verb.
- A `resources/read` of an unknown URI holding a control character no longer ends the MCP session, and the reply no longer repeats the URI. An API error's message is marked untrusted in the structured error.
- Messages that quote text from the caller, the configuration or the audit log are escaped: `doctor --json`, the flag package's errors, the MCP server's warnings, the warning for a read that was not audited, and the paths that `audit verify`, `audit rotate` and `docs --check` print.
- A result printed as text that cannot be written in full makes the command exit 1. `tailkeeper docs` refuses an argument it would have ignored, and `docs --help` exits 0.
- On Windows, the audit-log appends of one process are serialised, so the parallel calls of one MCP server no longer break the chain; two processes writing at once still can.
- `audit verify` warns on standard error when an archive it continues is missing, and a failure to close the audit log after an append is reported.
- With a privacy key, the length cap no longer leaves half a pseudonym marker at the end of a cut value. Entries of a result's map whose keys are the same text once escaped or cut are all kept, with a counter (`#2`) after the first, instead of all but one being dropped.
- `filter_refused` says what a filter takes, and whether a privacy key is needed for pseudonyms; `devices_list user=tagged-devices` works while masked; the `includeValues` previews and the digests are described exactly.

### Changed

- The repository starts a fresh public history at 0.5.0. Earlier releases (0.1.0 to 0.4.0) are described below but were not published.
- While personal data is masked, `devices_list` refuses a `hostname` filter that masking would change (an email address, a public IP address, or text that looks like one) (`filter_refused`), `nameContains` matches the name as shown, and a device is looked up by its hostname as the result shows it: use the node ID for a device whose hostname masking changes.

## 0.4.0 — 2026-10-12

Masking stops confirming guesses, and masked values get names. tailkeeper's API coverage is now checked against Tailscale's own OpenAPI document.

Upgrading: while personal data is masked (the default), `devices_list --user` with a login, and `audit_log` with a `~search` or an address as `actor` or a non-ID `target`, are refused with `filter_refused`. Use the pseudonym a masked value carries, or set `personalData` to `show`. `audit_log`'s `oldSha256` and `newSha256` are now `oldDigest` and `newDigest`.

### Added

- A privacy key (`TAILKEEPER_PRIVACY_KEY`, 64 hexadecimal characters), kept where the read credential is. It names every masked identifier and email address in a result with a pseudonym (`a…@example.com [p:k7x2m9qd4a]`), stable across calls and tools, and keys `audit_log` digests. Error messages, and the reasons `acl_test` returns, are masked without pseudonyms: they echo what the caller typed, and a pseudonym beside a guess would confirm it. `doctor` reports it.
- Filters take pseudonyms: `devices_list`'s `user`, `audit_log`'s `actor` and `target`, matched client-side. With masking off, `audit_log` refuses a list that mixes a pseudonym with a `~search` or a substring (`validation_failed`), which a client-side match would silently drop.
- `audit_log`'s `target` pseudonym matches an entry only through an address its target name shows, one pseudonym per address, and only while that pseudonym is still displayed: not the pseudonym of the name as a whole, and not one the length cap cuts off. Text cannot forge one (see Changed). With masking off, a pseudonym filter no longer matches a whole name that is not an address.
- A privacy key that is set but malformed or unreadable is reported once when the MCP server starts, and `audit_log`'s note says so instead of that no key is loaded. Masking still runs, without pseudonyms or digests.
- `audit_log`'s `actor` and `devices_list`'s `user` pseudonyms match only a pseudonym the display shows: not that of a value masking leaves as it is (the owner of tagged devices) and not one the length cap cuts off.
- An MCP call to a tool the server hides (today the two alpha OAuth-app tools, without `--enable-alpha`) returns `tool_hidden` with the setting that shows it, and the server's instructions list the hidden tools.
- `docs/tools.md` maps every read operation in a pinned list of the operations in Tailscale's OpenAPI document to the tools that call it, or the reason none does; a test fails on any gap. A weekly job compares the pin with the live document.

### Changed

- While masking is on, filters that would confirm a guessed personal value are refused (`filter_refused`, exit 2).
- With a privacy key loaded, a `[p:` written in untrusted free text (a target name, a tag, an `includeValues` preview) is shown with its bracket spelled as an escape, `\u{005B}p:`, so that a pseudonym marker in a result is one tailkeeper appended and a member cannot plant one beside a hidden address. This is the only change to a result's text; with no key, and in the policy file and `acl_test` reasons, which no filter reads, text is shown as before.
- `audit_log` returns `oldDigest` and `newDigest`: an HMAC under the privacy key while masking is on, a SHA-256 when it is off, and nothing while masking is on without a key.
- `audit_log` orders entries that share a timestamp by a hash of the entry as displayed, so no raw login or old or new value feeds it. A `nextCursor` is good only with the same filters, limit and `includeValues`, the same masking setting and the same privacy key; otherwise `validation_failed`.
- New error codes: `filter_refused` (2), `privacy_key_unavailable` (5), `tool_hidden` (2).

## 0.3.0 — 2026-10-11

Two policy tools, pulled forward read-only from the spec's M3 (the ACL engine).

### Added

- `acl_get` (`tailkeeper acl get`): the tailnet policy file as the API returned it (HuJSON, comments included), a page at a time (`fromLine`, `nextLine`; `maxBytes`, default 150 KiB, measured as escaped JSON text, and a line longer than the page is refused with the size to ask for), with the size and SHA-256 of the whole policy and whether it is managed outside the admin console (`unknown` when the settings cannot be read, never `false`). Email addresses are masked unless `personalData` is `show`; addresses, CIDRs, hosts, tags and comments stay whole. While masking is on, the size and SHA-256 are those of the policy as shown, every page joined, and the ETag is left out, so none of them can confirm a guessed address; with `show`, they describe the file as the API returned it, ETag included. It is a display copy, not the file to edit. The CLI prints the facts, a notice that the policy is untrusted text, then the policy behind line numbers. In MCP it is in the default `reads` profile: the whole policy goes to the model provider when an agent reads it.
- `acl_test` (`tailkeeper acl test SRC --accept DST --deny DST [--proto P]`): whether one source can or cannot reach destinations under the live policy, without changing it. Pass or fail with Tailscale's reasons, one per line in the CLI after a notice that they are untrusted text; the CLI exits 9 on a failure. A source or destination Tailscale cannot resolve fails the test, with its reason. A pass is read only from a response shape Tailscale documents, with no field unknown or given twice; any other answer is an error, never a pass. Evaluated with no posture attributes; SSH rules are not tested. It refuses masked values, wildcards, CIDRs, unbracketed IPv6 and more than 32 destinations.
- `doctor --probe` checks `acl_get` and sends `acl_test` a test no policy can pass. A failure carrying Tailscale's reasons shows that failures are read as such and that the read credential may run tests; a pass is reported as a failure, and a refusal by the endpoint, or warnings alone, as a warning.

### Changed

- Apart from the credential's token request, the API client sends one request other than GET, `POST .../acl/validate` on its own tailnet, which Tailscale documents as never changing the policy. Its outermost transport refuses every other request but GET, for every credential kind, and the fake API fails any test in which one gets past it.
- A result field tagged `multiline` keeps line feeds and tabs (CRLF shown as LF); every other invisible character is still escaped. Escaping now also covers the default-ignorable code points and variation selectors it missed, such as U+034F and U+180B.
- Email masking reads JSON escapes inside an address (`\u0040` as an at sign, `\u0061` as a letter), which a policy file may use and Tailscale decodes, and masks a chain such as `a@b@c.d` whole instead of leaving `b@c.d` readable.
- `docs/tools.md` lists, per tool, the fields whose email addresses alone are masked.
- MCP tools can declare a larger result size for the host; `acl_get` declares 200,000 characters.

Fixes for the findings an audit of 0.1.1 left open. Tool results now mask personal data by default, so a consumer that read whole login names or public addresses sees them masked until the owner sets `"personalData": "show"`.

Upgrading: restart MCP hosts that still run 0.1.x before the first `tailkeeper audit rotate`. ### Changed

- Personal data is masked by default (spec Appendix C), in CLI and MCP results and in error messages. Identifiers are masked whole to their first character, plus the domain of an email address (`a…@example.com`): device owners, users' login and display names and tailnet ID, invite and contact emails, invite acceptors, configuration audit-log actors, webhook creators, `local_whoami` and `local_whois` users, the log-stream user, and the `operator` and `nickname` preferences. - `tailkeeper audit tail` shows the first four characters of the tailnet ID, as `doctor` does, unless `personalData` is `show`.

- Dependabot proposes a release only once it is a week old.
